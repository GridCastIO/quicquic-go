## Packet I/O and socket ownership

Receive coalescing is enabled on transport-created sockets and on supported external Linux and Windows sockets explicitly registered through `ConfigureExternalPacketIOV1`. External permission requires exclusive packet I/O and terminal socket disposal by the existing owner. Registration does not transfer close ownership, and `Transport.Close` does not restore ordinary raw reads; borrowed sockets intended for reuse must not grant receive-coalescing permission. The [registration API comments](../external_packet_io.go) define the exact contract.

For reusable sockets, `NewManagedPacketEndpointV1` creates an endpoint with exclusive leases. `ConfigureManagedPacketIOV1` binds a lease to the transport. Managed Linux and Windows endpoints retain a normalizing receiver across leases, so endpoint/lease `ReadFrom` continues returning one UDP datagram. Lease close interrupts and joins its I/O and permits reuse; `Transport.Close` alone does not release the lease. Lease return discards already consumed QUIC storage without draining kernel-queued traffic. Endpoint close is terminal. See the [managed endpoint contract](../managed_packet_endpoint.go).

`ConfigureFixedPeerV1` fixes a transport's permitted UDP peer before initialization, guarding receive, ordinary/batched/stateless output and alternate paths. It does not authenticate peer identity or enable migration. The [release notes](https://github.com/the-sarge/quic-go-fast/releases/tag/v0.62.1-fast.8#bundle-behavior-and-consumer-decisions) describe the opt-in network/setup admission, candidate selection and receive-phase extensions.

Multipath V1 is included in fast.10, absent from fast.9, experimental and opt-in; disabled is the default, and connections without it remain ordinary QUIC connections. Its one supported profile is draft-21 QUIC v1 with default Reno primary/backup or explicitly selected BBR primary/backup or aggregate and at most two paths, on Linux amd64 and on Darwin arm64 running Darwin kernel 27 (macOS 27). Darwin arm64 support is on `main` after v0.63.0 and is unreleased; v0.63.0 and fast.10 admit only Linux amd64, and Darwin requires the next minor release (see the [Unreleased changelog](../CHANGELOG.md#unreleased--next-minor-release)). Reno was qualified with Go 1.26.11 and 1.27.4 on the recorded Ubuntu 26.04.1 image with kernel `7.0.0-30-generic`; another toolchain or kernel is outside the tested evidence. On macOS, the same profile was qualified natively on one Apple-silicon host running macOS 27.2.1 (Darwin 27.2.0): every row with Go 1.27.4, and the endpoint, race and public-API rows also with Go 1.26.11; macOS 27.0 and 27.1 are admitted by an applicability assessment, not by observation, and Intel Macs, iOS and other macOS majors are refused. The [macOS support record](audits/2026-11-19-macos-multipath-q2-support.md) owns that evidence and its limitations. Enable it with `Config.ConfigureMultipathV1(true, 2, "primary-backup")`. A caller's socket needs an explicit `Transport` with the `Transport.ConfigureMultipathIOV1` grant, an exact unconnected `*net.UDPConn`; `Dial`, `Listen` and HTTP/3 `Server.Serve` refuse it, while the `Addr` helpers and HTTP/3's default client grant the sockets they own. Other platforms, a `Config.Versions` that lists QUIC v2 and excluded transport configurations (fixed-peer or network admission, candidate groups, send-thread QoS, packet ceilings, external or managed packet I/O) fail with `ErrMultipathUnsupportedV1` before anything is advertised; `ConfigureMultipathV1` accepts only `"primary-backup"` or `"aggregate"` and one or two paths, returning `ErrMultipathInvalidConfigV1` otherwise. Aggregate requires `SetCongestionControlV1("bbrv3")`; either setter order works, and every constructor rechecks the final pair so a later change to Reno is refused with `ErrMultipathUnsupportedV1`. A connection that negotiates QUIC v2, or whose peer doesn't negotiate multipath, stays ordinary; check `Conn.MultipathNegotiatedV1`. Before closing a `Transport` that surviving paths may still use, wait on `Conn.WaitTransportDetachedV1`; after `Transport.Close`, `Transport.WaitMultipathIOStoppedV1` returns the socket's write authority. The qualification evidence is the [native receipt](audits/2026-11-03-multipath-e6-receipt.md), carried to those Go patch releases by the [November compiler reassessment](adr/2026-10-24-multipath-endpoint-plan.md#november-go-patch-reassessment), with its [writer-yield supplement](audits/2026-11-12-native-writer-yield-r21/README.md), the [independent interoperability receipt](audits/2026-11-09-multipath-r17-receipt.md) and the [ordinary-peer cost receipt](audits/2026-11-12-multipath-r18-delivery-receipt.md), which keeps two owner-accepted CPU-per-useful-byte exceptions. BBR's public primary/backup evidence and exact accepted cost exceptions are recorded in the [B9 support receipt (#1382)](audits/2026-11-15-bbr-b9-support.md), including six native Go 1.27.4 interoperability cases through public admission. BBR aggregate is experimental after B11’s positive fixed comparison; the [B12 support record (#1385)](audits/2026-11-15-bbr-b12-support.md) owns its aggregate evidence. Reno aggregate remains refused; B5’s negative comparison concerns the retired arrival policy. Additional validated paths start as local backups: each sending endpoint must call `Path.SetLocalUseV1("active")` on the paths it intends to use concurrently. Selecting aggregate alone does not activate them; `Path.StateV1` reports their local use. Backups remain excluded from ordinary aggregate work while an active path is eligible, with existing PTO precedence unchanged. The underlying BBRv3 controller remains experimental and unqualified while full [Q2 (#599)](https://github.com/the-sarge/quic-go-fast/issues/599) is deferred. No consumer adoption recommendation follows. Isolate these calls in an integration adapter, like the other fork additions.

The [Linux ARM64 implementation and qualification plan (#1395)](adr/2026-11-19-linux-arm64-multipath-plan.md) describes future full-profile support. It does not enable ARM64 multipath or establish native qualification.

The [ordinary-flow cost comparison (#1368)](https://github.com/the-sarge/quic-go-fast/issues/1368) measured the native endpoint against an unregistered, controller-matched BBR baseline on the recorded Linux venue. Across three paired rounds per workload, ordinary goodput was 0.944295141271208 of baseline with mixed background traffic and 0.9590708299335772 under stateless-packet pressure; server CPU per useful byte was 1.2081314772756437 and 1.1593702973325581 times baseline, respectively. The CPU denominator includes useful background bytes in the mixed workload. The owner accepted these exact measured tradeoffs: mixed-bulk misses the original 0.95 goodput floor and 1.10 CPU ceiling, while stateless-pressure misses CPU; the raw verdicts remain failed. All other qualification checks and the six BBR interoperability cases pass. The [final receipt](audits/2026-11-14-bbr-ordinary-cost-1368/final-qualification/README.md) records the source, workload, measurement-only overlays and evidence limits. B9 (#1382) separately enables experimental public BBR primary/backup after checking source applicability and public peer evidence. The original measured exceptions do not become tolerances for future changed workloads. Aggregation, full Q2 (#599) and application qualification remain outside that decision.

A grant covers the whole transport, not only its multipath connections. Every connection dialed or accepted on a granted transport, including ordinary ones that never negotiate multipath, sends through the native endpoint, the socket writer the grant installs, and so does `Transport.WriteTo`. For connections, an expired local queue or write deadline there is backpressure, not a send failure: the connection stays open, bounded by its usual handshake, idle and path-validation timeouts. `WriteTo` instead returns `ErrMultipathBackpressureV1`, plus `ErrMultipathDeadlineV1` when its deadline expired; neither proves the packet was not sent. Each endpoint has a budget of 4,096 participants, shared by ordinary and multipath connections: a connection takes one on its own transport and one on each other granted transport it sends from through `Conn.OpenPathV1`, `Path.MigrateV1` or `Conn.AddPath`. When a transport's budget is full, a dial on it fails with `ErrMultipathResourceLimitV1`, and its server refuses a new connection with CONNECTION_REFUSED, or drops the first packet when it cannot send the refusal in time. A connection that needs a new participant there also gets that error from `OpenPathV1` from it or `MigrateV1` to it, and skips an `AddPath` probe from it until its probe timer retries. Closing a connection does not promise to free its participant at once.

## Migrate jumbo recovery for JR1

**Availability:** this behavior is on `main` following [PR #1477 — Restore jumbo with repeatable fallback](https://github.com/GridCastIO/quicquic-go/pull/1477), implementing [JR1 (#1476)](https://github.com/GridCastIO/quicquic-go/issues/1476). It is unreleased and is not part of v0.63.0. It requires a minor release under the [version-aware compatibility promise](adr/0016-version-aware-compatibility.md), even though the public method signatures are unchanged. Select the eventual published version explicitly; the [Unreleased changelog](../CHANGELOG.md#unreleased--next-minor-release) is preparation material, not an available dependency version.

### Who needs to migrate

Review applications that opt into jumbo packet ceilings through `Transport.ConfigurePacketCeilingV1` and assume the connection stays at standard sizes after its first fallback. Connections using the default 1452-byte ceiling, or whose peer caps them at standard sizes, retain their existing behavior. Jumbo still requires configuration before Transport initialization and remains incompatible with native multipath I/O. JR1 changes no module imports, public API signatures or minimum Go version; Go 1.26.0 remains the minimum.

In v0.63.0, the first jumbo fallback permanently prevents further jumbo searches on that connection. With JR1, confirmed fallback permits later searches on the same connection. On the same path, the first cooldown is 60 seconds from fallback confirmation. If migration interrupts that first fallback before confirmation, the first cooldown can instead start at cutover, subject to the retained-state rule below. Completed searches that do not restore jumbo near the current path ceiling schedule 120, 240, 480 and then 900 seconds from completion, saturating at 900. Successful restoration stops periodic searching but retains accumulated backoff for a later fallback. These are retry intervals, not a recovery deadline: a deadline permits a search, while only a live probe acknowledgment permits larger application packets. Discovery continues to use ordinary pacing, congestion admission and loss processing.

Migration preserves an armed absolute deadline or elapsed eligibility and accumulated backoff. A new path runs standard-size discovery under existing rules; jumbo still requires that path's successful standard-stage admission and the retained cooldown. If no deadline or elapsed eligibility survives, migration after a prior fallback schedules the next interval once from cutover. Post-fallback searches respect the destination Transport's ceiling, even when it is lower than the original negotiated ceiling.

### Update application assumptions

| Surface | JR1 behavior | Consumer action |
| --- | --- | --- |
| `PathMTUFallbackV1` | The same channel closes once on the first actual size drop. It does not confirm smaller delivery, and later growth or repeated fallback produces no new closure. It remains nil on a Transport that was not configured for jumbo. | Handle closure once as a historical first-drop event. Remove assumptions that it means jumbo is permanently disabled or that it reports every recovery episode. Remove a handled closed channel from a recurring `select` so it cannot continuously fire. |
| `PathMTUSettledV1` | The same channel closes once when discovery ends on the first path, the connection leaves that path or discovery cannot run; connection termination also settles it. Later retry, growth, shrink and migration do not reopen or replace it. | Treat closure as notification that first-path discovery is over. It is not proof that a search ran, succeeded or validated a size, and it is not a stable packet-size or DATAGRAM-limit promise. |
| Transport DATAGRAM admission | `SendDatagram` may refuse a message after shrink; live probe acknowledgments can later raise admission again. Admission does not guarantee delivery. | Continue handling `DatagramTooLargeError` and apply the application's existing fragmentation, rejection or sizing policy when a message no longer fits. Do not treat a prior successful send as a permanent size guarantee. |
| Consumer-published application DATAGRAM limit | The application's published or negotiated message limit remains fixed. JR1 does not make that application contract dynamic. | Keep the published limit fixed for its existing lifetime. A larger transport admission allowance does not authorize publishing or sending messages beyond the application's own contract. |
| `PathMTUInfoV1` | The effective ceiling remains the original negotiated observation, including after migration. The tested stage-one report survives a cooldown-driven same-path restart until a newly validated result replaces it; migration or confirmed initial-size recovery still resets it while standard discovery restarts. | Use these values as observations of negotiation and tested fallback. Neither is the current maximum application DATAGRAM payload or permission to grow it. A destination Transport can impose a lower search ceiling than the negotiated observation. |
| Idle lifetime | Retry PINGs and their ACKs refresh ordinary idle accounting. Repeated cycles with acknowledged smaller probes can extend an otherwise idle connection, including with `KeepAlivePeriod` disabled. There is no separate keepalive override or idle recovery deadline. | If the product requires an application-inactivity deadline, enforce it from application activity and close/cancel according to that policy. Transport idle timeout or `KeepAlivePeriod = 0` alone does not express that requirement. |

A changing path can now cause repeated growth and fallback interruptions. A reconnect is no longer the only supported route to jumbo recovery, but JR1 does not promise when an idle or impaired connection will regain it. If the application requires standard-sized connections, create them on a Transport with the default 1452-byte ceiling, or configure that ceiling before initialization. JR1 adds no per-connection setting that permanently disables retries after the first drop; do not mutate a sealed Transport to emulate one.

### Adoption and evidence

Check fallback handling, DATAGRAM sizing and application-inactivity policy against the assumptions above, then exercise recovery and another shrink in the application's own workload. Keep the consumer-published DATAGRAM limit fixed during that evaluation. The Evidence section of [PR #1477](https://github.com/GridCastIO/quicquic-go/pull/1477) reports repeated local and far-side recovery with Reno and BBR using streams and fixed-size application DATAGRAMs. The [JR1 finite-evidence contract](adr/2026-11-18-jumbo-reclimb-plan.md#jr1--restore-jumbo-with-repeatable-fallback) names the migration, threshold, stale-feedback and blocked-send completion cases. The [final local certification for PR #1477](https://github.com/GridCastIO/quicquic-go/pull/1477#issuecomment-6999228101) records the exact-head checks. Those are implementation evidence, not physical-link qualification, a throughput result or a general interruption bound. The [JR1 contract](adr/2026-11-18-jumbo-reclimb-plan.md) retains the policy and evidence boundary; the [release runbook](runbooks/release.md#jr1-minor-release-handoff) owns candidate-specific release validation and publication.

## Platform controls

Offload availability depends on the host, packet-I/O path and explicit permissions. Generic platform CI does not prove native offload engagement. Qualified macOS batching uses the private `sendmsg_x` syscall with kernel qualification and a startup self-check. Build with `-tags quic_go_no_private_syscalls` to disable private-syscall paths.

On macOS, a participating wrapper implementing `ReadBatch` and `ReadBatchSlotsV1Conn` can opt into multiple datagrams per read; the default is one slot. Each buffer is one byte larger than the largest packet; a completely filled buffer is treated as truncated and dropped. The adapter owns its receive call; see the [read-slot API contract](../sys_conn.go) for bounds and platform exclusions. This is distinct from the fork's retired standalone `recvmsg_x` receive-batching experiment. Apple-silicon macOS also offers opt-in send-thread QoS through `ConfigureSendThreadQoSV1`; see its [contract and per-connection status](../send_thread_qos.go).

Set these environment variables to `true` to disable the named behavior:

| Variable | Effect |
| --- | --- |
| `QUIC_GO_DISABLE_GSO` | Disable segmented send, including Windows USO |
| `QUIC_GO_DISABLE_GRO` | Disable Linux GRO and Windows URO receive coalescing |
| `QUIC_GO_DISABLE_SHORT_GSO_SEGMENTS` | Disable equal-size short-DATAGRAM batching; full-size segmentation remains available |
| `QUIC_GO_DISABLE_SENDMSG_X` | Disable macOS batch send |
| `QUIC_GO_DISABLE_RECVMSG_X` | Keep one macOS adapter read slot |
| `QUIC_GO_DISABLE_SEND_QOS` | Disable send-thread QoS for new connections |

## Trace privacy

Qlog traces can contain sensitive HTTP headers and QUIC tokens. The QUIC and HTTP/3 default tracers create missing `QLOGDIR` directories with mode `0700` and new trace files with mode `0600`, subject to umask on Unix. Existing directory permissions are preserved; choose a trusted directory and parent path. An existing trace path, including a symlink, disables tracing for that connection instead of overwriting it. Restrict access to trace archives and review them before sharing.

## Migrate to quicquic-go

quicquic-go declares module `github.com/GridCastIO/quicquic-go` and keeps the root package name `quic` ([ADR 0014](adr/0014-independent-module-identity.md)). [v0.63.0](https://github.com/GridCastIO/quicquic-go/releases/tag/v0.63.0), published November 17, 2026, is the first release under this path.

1. **Change imports.** Replace the `github.com/quic-go/quic-go` prefix with `github.com/GridCastIO/quicquic-go` in root and subpackage imports, for example `github.com/GridCastIO/quicquic-go/http3`. Use that exact case: `github.com/gridcastio/quicquic-go` is a different module path and fails with a path mismatch, and the module cache stores the path as `github.com/!grid!cast!i!o/quicquic-go`. Identifiers such as `quic.Config` and `http3.Server` do not change. For example, to rewrite quoted import paths in place:

   ```sh
   git grep -lz 'github.com/quic-go/quic-go' -- '*.go' |
     xargs -0 perl -pi -e 's{"github\.com/quic-go/quic-go((?:/[^"]*)?)"}{"github.com/GridCastIO/quicquic-go$1"}g'
   ```

   `goimports` and the `goimports` formatter in golangci-lint write the root import as `quic "github.com/GridCastIO/quicquic-go"`. The path's last element is not the package name, so they add the explicit name. Accept it; it changes nothing else.
2. **Require the release.** Run `go get github.com/GridCastIO/quicquic-go@v0.63.0` and select later versions explicitly under the [compatibility promise](adr/0016-version-aware-compatibility.md). Inherited tags such as `v0.62.0` and the `v0.62.1-fast.N` prereleases are not quicquic-go releases. Those with a `go.mod` file declare an old path, so Go rejects them for the new one, as the [release record](releases/v0.63.0.md#publication-results) shows. A few pre-module tags such as `v0.10.1` can still resolve under the new path, but they are not supported versions: v0.63.0 retracts every earlier tagged version, so Go warns if one is selected.
3. **Drop the old replacement.** After migrating imports, and any dependencies as in step 4, run `go mod tidy` with the replacement still in place; this removes your own now-unused requirement on the old path. Then check that `go mod why -m github.com/quic-go/quic-go` reports the module is not needed and `go mod graph | grep 'github.com/quic-go/quic-go@'` prints nothing. If either still shows the old path, a dependency still requires it; investigate that dependency rather than removing the replacement. Once both checks are clean, run `go mod edit -dropreplace=github.com/quic-go/quic-go` and `go mod tidy` again, and commit `go.mod` and `go.sum`.
4. **Migrate dependencies that expose QUIC types first.** Defined types from the old and new paths are distinct, so a `*quic.Conn` from one cannot be passed where the other is expected. A dependency whose API exposes QUIC types must move to the new path before or together with your application. For GridCast and tapmux, that means wiremux's cutover in [GridSwarm/wiremux#2175](https://github.com/GridSwarm/wiremux/issues/2175) comes first. Until then, the old module stays in the graph alongside the new one.
5. **Keep existing adaptations.** Use keyed literals for `Config` and every other exported struct from this module. Positional literals are outside the compatibility promise, and some, including `Config`'s, already do not compile. Inspect HTTP/3 errors as the [error-handling guide](../http3/README.md#error-handling) describes. Go 1.26.0 remains the minimum.

From fast.10, the module path is the only difference: no Go source changed except identity. From upstream v0.62.0, also expect the differences the [changelog](../CHANGELOG.md) records for the fast series, including:

- this project's additional `...V1` APIs, among them packet I/O, managed endpoints, fixed peers, admission, congestion-control selection, DATAGRAM admission, jumbo and multipath;
- the 128-entry DATAGRAM send queue and the 1,024-entry receive queue;
- the reassembly gap limit of 4,096;
- the qlog `Path` fields that break positional literals;
- HTTP/3 error conversion and stricter header validation.

The [fast.10 release record](releases/v0.62.1-fast.10.md#compatibility-and-support) lists the latest of these.

To roll back, return to the previous source and dependency state through ordinary version control. To return to upstream quic-go, first remove or adapt calls to this project's additional APIs, then restore the `github.com/quic-go/quic-go` imports and requirement. Verify the selected upstream version and your application's compatibility before deployment.

## Development toolchains

Use Go 1.27.4 for repository maintenance; [`.go-version`](../.go-version) records that choice for version managers that support it. The Go command itself does not read this file. Select the exact maintainer or compatibility toolchain explicitly:

```sh
GOTOOLCHAIN=go1.27.4 go test ./...
GOTOOLCHAIN=go1.26.11 go test ./...
```

These commands may download the named toolchain but do not permit automatic upgrades beyond it. CI installs the exact version for each lane, sets `GOTOOLCHAIN=local` to prevent automatic toolchain switching, and verifies the effective version. Integration CI also verifies the FIPS and vendor fixture modules. The root and nested integration modules retain their `go 1.26.0` language minimum. When reproducing a compatibility lane with a version manager, select Go 1.26.11 explicitly and use `GOTOOLCHAIN=local`.

The development journal records merged work and validation, and [DEV-JOURNAL.md](DEV-JOURNAL.md) holds its entries recorded in this repository; [GLOSSARY.md](../GLOSSARY.md) defines domain terminology; the [release runbook](runbooks/release.md) describes publication.
