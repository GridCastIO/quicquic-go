## Scope

v0.63.0 is the first independent release of quicquic-go: module `github.com/GridCastIO/quicquic-go`, root package `quic`, repository `GridCastIO/quicquic-go` after #1110. It starts the project's own numbering under [ADR 0016](../adr/0016-version-aware-compatibility.md); the `-fast.N` series ends.

The prepared source is fast.10's runtime source with the identity transition applied. Between `v0.62.1-fast.10` (`24d75daf288469e454f55717ec20463eaf87675a`) and the preparation base `f05a8a4a1e6c766936d154759171e7a98955fdb6`, no Go file changed. [PR #1461](https://github.com/the-sarge/quic-go-fast/pull/1461) changes only module identity, verified by its normalized-equality and import-scan receipts. The accompanying documentation change, stacked on it, changes documentation and the root `quic` and `http3` package comments. Runtime behavior, wire format, API names and signatures, defaults and experimental qualifications are therefore those of fast.10. At the final home, `main` gained only these two changes, merged unchanged, their development-journal entry and the release-commit change, which adds the retraction below, finalizes this record and the README, runbook, changelog and usage wording, and adds the [release plan](../adr/2026-11-17-quicquic-v0.63.0-release-plan.md); no other Go source or dependency changed.

Ancestry: the project derives from quic-go, and v0.62.0 is its historical baseline. The version number promises neither parity with nor tracking of upstream ([ADR 0015](../adr/0015-independent-maintenance.md)). Go 1.26.0 remains the consumer minimum; development uses Go 1.27.4, with compatibility CI on Go 1.26.11. Root dependency requirements are unchanged from fast.10. No binary or container assets are distributed.

Outside this release: the [wiremux cutover (GridSwarm/wiremux#2175)](https://github.com/GridSwarm/wiremux/issues/2175) and the application cutovers that follow it; public interop-runner registration [#1112](https://github.com/the-sarge/quic-go-fast/issues/1112); and building the upstream-advisory monitoring workflow designed in the [advisory runbook](../runbooks/upstream-advisories.md).

## Migration summary

The [migration guide](../usage.md#migrate-to-quicquic-go) is authoritative. In brief:

- Change root and subpackage imports from `github.com/quic-go/quic-go` to `github.com/GridCastIO/quicquic-go`, with that exact case. Identifiers such as `quic.Config` are unchanged. `goimports` writes the root import as `quic "github.com/GridCastIO/quicquic-go"` because the path's last element is not the package name.
- Once v0.63.0 is published, require it with `go get github.com/GridCastIO/quicquic-go@v0.63.0`. After migrating imports, run `go mod tidy` with the old replacement still in place, then drop the replacement only once `go mod why -m` and `go mod graph` show nothing still requires `github.com/quic-go/quic-go`, and tidy again.
- Old-path and new-path types are distinct. A dependency that exposes QUIC types in its API, wiremux first, must move to the new path before or together with the application.
- Callers coming from fast.10 see no other difference. Callers coming from upstream v0.62.0 also take the existing differences: keyed `Config` literals, HTTP/3 error handling, qlog `Path` fields and the documented fork APIs and defaults.

## Retraction of earlier versions

On 2026-11-17, Josh decided to retract every version below v0.63.0 ([decision record](https://github.com/GridCastIO/quicquic-go/issues/1111#issuecomment-6953255891)). Eleven inherited tags from upstream's pre-module history have no `go.mod`. Nine of them, `v0.5.0` through `v0.10.1`, including the two `-no-integrationtests` tags, are canonical module versions, so Go synthesizes a `go.mod` with whatever path is requested and they can still resolve as versions of `github.com/GridCastIO/quicquic-go` when explicitly requested; the other two, `v0.4` and `race`, are not canonical versions. Retraction does not stop those nine from resolving: it removes them from version lists and `@latest` and makes Go warn when one is selected. The release's `go.mod` therefore carries:

```
// Versions before v0.63.0 are inherited upstream quic-go history, not releases of this module.
retract [v0.0.0, v0.62.99]
```

Every canonical tag inherited from upstream and the fast series falls inside that interval. Pseudo-versions of commits with no earlier canonical tag (`v0.0.0-<timestamp>-<hash>`) sort below `v0.0.0` and fall outside it; Go never lists them or selects them for `@latest`, so a consumer reaches one only by naming an old commit. Go reads retractions from the latest version's `go.mod`, so later releases keep the directive.

After tagging, #1111 records here:

- `go list -m -retracted -versions github.com/GridCastIO/quicquic-go` lists the pre-module versions (the listing carries no retraction marker), and `go list -m -retracted -f '{{.Retracted}}' github.com/GridCastIO/quicquic-go@v0.10.1` prints the rationale;
- `go list -m -versions github.com/GridCastIO/quicquic-go` omits them;
- in a fresh consumer, `go get github.com/GridCastIO/quicquic-go@v0.10.1` warns that the version is retracted;
- `@latest` resolves to v0.63.0.

## Scanner coverage

Go vulnerability records name affected module paths, and `govulncheck` looks them up by module path. When a module is replaced, it looks up the replacement's path and version: see [`fetch.go`](https://github.com/golang/vuln/blob/e672cbe8fbc8c76e28fcb6db0efd9ce354e0dac5/internal/vulncheck/fetch.go#L13-L24) and the [module lookup](https://github.com/golang/vuln/blob/e672cbe8fbc8c76e28fcb6db0efd9ce354e0dac5/internal/client/client.go#L193-L225) at the pinned revision. Records for inherited upstream code name `github.com/quic-go/quic-go`. A scan of `github.com/GridCastIO/quicquic-go`, at any version, therefore does not report them, and an empty result does not show that inherited code is unaffected. Fast-series consumers who replaced `github.com/quic-go/quic-go` with `github.com/the-sarge/quic-go-fast` were looked up under the replacement path and likewise received none of these records.

This applicability record supplements the release scan and the versioned consumer scan; it does not replace them. Do not falsify a module path, for example by declaring or replacing the old path, to obtain scanner output. How the scanner treats this repository's own main module was not separately established.
