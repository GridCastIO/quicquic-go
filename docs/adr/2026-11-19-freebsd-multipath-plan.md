# FreeBSD multipath implementation and qualification plan

**Date:** 2026-11-19. **Identity:** MP-FBSD-1398, revision 1. **Status:** owner-approved planning scope; implementation and qualification pending. **Issue:** [Plan multipath support for FreeBSD (#1398)](https://github.com/GridCastIO/quicquic-go/issues/1398). The owner approved this documentation-only work through review and merge after confirming the infrastructure controller on m4mini. Completion publishes a plan; it neither enables FreeBSD multipath nor dispatches the future slices, provisions infrastructure, runs qualification, or allocates campaign capacity.

## Outcome and source authority

Plan equivalent supported public behavior and ownership guarantees to the existing Linux amd64 profile on both `freebsd/amd64` and `freebsd/arm64`. The [maintainer decision on issue #1398](https://github.com/GridCastIO/quicquic-go/issues/1398#issuecomment-7001061738) makes both architectures initial targets, including Reno primary/backup, experimental BBRv3 primary/backup and experimental BBRv3 aggregate. Different kernel mechanisms, syscall counts and performance are allowed; missing access or an unrun test is an evidence gap, not proof that a feature is impossible. A reduced feature profile requires concrete technical evidence, alternatives and an explicit maintainer decision. Defer `freebsd/386` and `freebsd/arm` from initial support because they are outside that selected qualification domain; preserve their existing build coverage.

The issue's historical baseline is `48dc6634fef404404647b7e64024303a52a4fb4e`. This plan inspected source at `0fbad183f7c92eba8fa234cb9194d87029e4014d`. Between those revisions, `multipath_api.go`, `multipath_admission_native.go` and `native_endpoint.go` change module imports only; `native_transport.go` and `sys_conn_helper_freebsd.go` are unchanged. This is a targeted owner audit, not a claim that the whole repository is unchanged. Recheck the source and toolchain pins before implementation.

The [endpoint contract](2026-10-24-multipath-endpoint-plan.md), [Reno contract](2026-10-24-multipath-reno-plan.md), [BBR contract](2026-10-24-multipath-bbr-plan.md) and [glossary](../../GLOSSARY.md) govern the preserved behavior. Do not reopen the completed [multipath program (#646)](https://github.com/GridCastIO/quicquic-go/issues/646) or [BBR continuation (#1374)](https://github.com/GridCastIO/quicquic-go/issues/1374), alter frozen receipts, or inherit their platform-specific exact-result exceptions. The [macOS planning issue (#1396)](https://github.com/GridCastIO/quicquic-go/issues/1396) and its [plan](2026-11-18-macos-multipath-plan.md) identify possible shared tooling work, not a dependency on macOS enablement or evidence transferable to FreeBSD.

### Qualification domain versus public admission

The proposed starting evidence is deliberately the exact 15.1-p5 kernel/architecture/toolchain domain above, not every FreeBSD build. Before F4, the maintainer must approve the public release applicability rule: retain a narrow runtime release domain at the common capability decision, or accept a documented wider release domain supported by additional applicability evidence. This plan recommends starting with the FreeBSD 15.1 RELEASE lineage, anchored by the p5 receipts, but does not pretend a p5 observation qualifies every patch, older release or future major. Pin image, kernel, Go runtime/poller source, hypervisor and relevant virtual NIC identities in each receipt; classify later kernel/runtime changes before reusing it.

If the chosen domain needs runtime release checking, keep it behind the same capability decision used by `ConfigureMultipathIOV1` and constructor admission, with independent positive and negative expectations. Kernel-reported version data owns the representation; define the accepted values and unknown/error disposition before implementing a detector. An unrestricted `GOOS == freebsd`/architecture predicate cannot be substituted without the applicability decision. No new detector is implemented or presumed proven here.

### Test seams and native method readiness

Use deterministic endpoint adapters for ownership/disposal and independently expected interleavings; they miss OS/poller behavior. Use existing private `configureNativeIO`/`startNativeEndpoint` root-package seams with real `*net.UDPConn` for pre-admission deadline, metadata and join evidence; they miss full public construction and independent interoperability. Use public constructors and the pinned independent peer for integration/wire evidence; they miss unexercised kernel failures and broad performance behavior. Preserve real packet construction at emission seams and independent expected outcomes. Later runtime fixes should proceed behavior-by-behavior through red/green at these seams, without creating an exported test bypass, environment override, fake OS identity or second deadline owner.

F1 first resolves a FreeBSD-native poller witness on both architectures. A candidate method is a narrowly scoped syscall-interposition fixture at the actual `sendmsg` boundary using FreeBSD's [ptrace facilities](https://man.freebsd.org/cgi/man.cgi?query=ptrace&sektion=2&format=html), then observing the unmodified Go write/wait/deadline path. The manual establishes syscall tracing and register access, not a working two-architecture injector; instruction/errno handling, write readiness, tracer permissions and process cleanup remain feasibility work. Tracing must be confined to the fixture's own process. Prefer a reproducible real-kernel trigger if one is demonstrated. An injected EAGAIN without observed write-wait traversal is insufficient. A wrapper returning EAGAIN above Go's poller, a raw C send alone, or an already-expired request cannot supply this witness. If neither method demonstrates traversal and bounded native return, record the missing evidence and return for a method decision before qualification; do not mask it with skipped tests.

Use the current-write witness for independent queued expiry and active-close/join. Keep a separate pressure observation using fresh sockets, recorded effective buffers, controlled sender/receiver load and native stack/error/drop observations. An unread loopback receiver or small buffer does not itself prove sender pressure; record a negative observation if no wait or ENOBUFS occurs. Do not expand into privileged network/device experiments without a concrete approved method. Instrumented traces establish attribution; uninstrumented native cases assess the existing 20 ms endpoint tolerance under its responsive-scheduler assumption. Report scheduler/topology and VM/host contention, distinguishing performance-core and efficiency-core activity where relevant, rather than treating a busy host as automatic contamination.

Native peer preparation should first build the existing pinned picoquic `fbd46d9a1f54ebf9397f2ee6355b5019ab379fb7` and PicoTLS `e446233b4100ebcdec60901c05bfb7f4cd369c5d` as local guest processes. Preserve library-owned wire parsing and the current adapter's bounded opaque replay/gating behavior. Check BSD socket layout/length fields, truncation semantics, loopback address binding and process cancellation/join. Use infra's supported artifact channel or an infra-owned prepared baseline for offline native dependencies; do not assume guest package/network access. A remote independent peer is a possible fallback only after its supervision/network/identity implications are reviewed. Linux-hosted subject execution cannot qualify FreeBSD.

The public peer inventory retains eight Reno primary/backup scenarios in both roles and three BBR scenarios in both roles for each policy. Fresh post-activation DATAGRAM evidence must identify new application payloads delivered through both active ingress paths, separately from cumulative counters and earlier backup-path traffic; retain the existing post-activation STREAM witness. Missing, duplicated, skipped or mismatched expected cases fail the claim. Freeze exact toolchain/architecture identities and native peer binary/dependency hashes in the receipts. These are proposed semantic inventories; this planning issue allocates no run attempts or campaign budget.

## Ordinary cost and aggregation measurements

Compare unregistered ordinary QUIC against the same source/binary with the endpoint grant on each architecture. Cover STREAM, DATAGRAM, mixed bulk, stateless/public response pressure, application echo/send-call latency, idle/backup/retired-path state and active-close completion. Measure actual FreeBSD scalar production routes; do not manufacture a GSO-on cell or call constructed software grouping a production comparator. Apply matched offered workload and receiver-verified useful delivery. No timing result is borrowed from Linux or from a traced run.

F3 supplies native process CPU accounting and RSS/peak memory with explicitly recorded units and sampling lifetime, using FreeBSD facilities such as `getrusage` and native process/sysctl observations rather than `/proc`. Maximum RSS is a process-lifetime high-water mark, not automatically a workload-window resident measure; choose and document the appropriate native measurement for each question. Capture guest CPU and scheduling plus host/hypervisor topology and competing work where observable. Missing counters remain unknown, not zero. Affinity changes or exclusive host reservations are not assumed. Infra owns lifecycle/isolation; the project owns workload/result meaning.

Reuse the applicable [accepted product thresholds](2026-10-24-multipath-reno-plan.md#accepted-product-thresholds) and [ordinary cost requirements](2026-10-24-multipath-reno-plan.md#r18--measure-ordinary-peer-costs-on-granted-endpoints): at least 95% baseline useful goodput, CPU/useful-byte ratio at most 1.10, native RSS growth at most 10%, and the existing p99 application echo/send-call latency ceiling. Application send-call latency measures `Stream.Write`/`SendDatagram`, not native completion or peer acknowledgment. Preserve raw numerical verdicts. FreeBSD receives no Linux latency/CPU exception; an exception or changed criterion needs a new explicit exact-result decision.

For aggregation, prepare a maintained successor to the retired comparison tools with controller-matched single-path, independent-connection, primary/backup and aggregate arms. Reuse the balanced disjoint-path, unequal-delay/rate and shared-bottleneck semantic topologies. The existing criteria ask for at least 20% useful-goodput improvement over the better single path and at least 95% of two matched independent connections on the balanced cell, plus no more than 10% harm to the ordinary Reno competitor relative to the independent-connection comparison on the shared bottleneck. Report asymmetric STREAM completion and DATAGRAM useful delivery separately. Establish relay rate/queue/clock fidelity and distinguish a userspace relay observation from a physical-network guarantee before collection. Feature correctness, experimental BBR status, ordinary costs and comparative benefit are separate verdicts.

A finite qualification protocol, workload windows and statistical question must be approved before F4 execution. This document neither chooses a new repeat count nor borrows the closed programs' capacity. Failed comparative evidence does not silently reduce the selected feature target: retain the result and return to the maintainer with alternatives and consequences. The support decision can only make claims justified by the selected native evidence.

## Ownership, artifact classes and alternatives

The present PR is process/traceability metadata only. Contract closure is **not triggered**: it introduces no runtime invariant or enforcement mechanism. Its representation domain is the finite source inventory, selected platform/profile table and named semantic classes. Git, typed source declarations and recorded infra metadata own those facts.
