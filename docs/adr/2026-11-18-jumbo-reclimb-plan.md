# Jumbo recovery after fallback

**Date:** 2026-11-18. **Identity:** `JR-1231`. **Status:** approved direction and retry policy; JR1 implementation accompanies this contract. **Design issue:** [Jumbo packets: design re-climbing after a fallback (#1231)](https://github.com/GridCastIO/quicquic-go/issues/1231). **Related program:** [Jumbo packets (#1215)](https://github.com/GridCastIO/quicquic-go/issues/1215). Source checked at `3bb45d0372ea1bf4e76705c79010821cce70e049`. The owner approved this design-PR scope and policy in the originating chat on November 18. Review history belongs in the merging PR, not in this normative contract.

## Outcome and boundary

Produce an audited implementation slice that lets a long-lived jumbo-active connection recover jumbo packetization after fallback. Successful padded probes must precede larger application packets. Retry intervals increase to reduce repeated interruptions on a changing path. The November 18 receiver-cutoff measurement in issue #1231 motivates this decision; its 272.708459 ms delivery gap and 56.8346% comparative goodput shortfall are one diagnostic example, not recovery deadlines or general throughput claims.

This decision supersedes the permanent post-fallback disable, its one-shot recovery wording and the rejected re-climbing alternative in the [original jumbo plan](2026-11-05-jumbo-packets-plan.md). Preserve the negotiated ceiling, fallback to the tested stage-one size and then the effective initial size, ordinary recovery rules, and the consumer's fixed published application DATAGRAM limit. The changing transport admission limit is distinct: `SendDatagram` may already refuse a message after shrink, and later confirmed growth may raise its limit. This plan does not make the published consumer limit dynamic.

No new configuration, exported method, dependency, worker, lock, channel, socket behavior, packet format, receive tier, fallback size or congestion algorithm is admitted. Unconfigured and peer-capped connections retain their existing behavior. Native multipath jumbo, initial discovery periodic retries before any fallback, equal-cost-path partial loss, real-link requalification, release claims, throughput targets and a general interruption bound are non-goals.

## Current enforcement and ownership

At the design source revision above, the connection run loop owns fallback and packet size. `applyPacketSizeFallback` and `watchingPacketSize` currently use `mtuFallback.started` as a permanent disable. `discoveryPacketCeiling` caps future paths after that first fallback. `startPacketSizeFallback` closes the public channel unconditionally and assumes there can be only one episode. The finder rejects stale probe callbacks with an 8-bit generation; repeated searches invalidate the original assumption that reset counts stay small. `Reset` clears stage-one observations, so it is unsuitable as an unqualified same-path retry operation.

The run loop already has recovery and discovery deadlines and emission preparation for Reno and BBR. Keep policy there. The finder owns search bounds and current-search probe receipts; emission owns real packet construction, registration and output handoff. Workers continue to report immutable local-refusal facts through the existing path-generation channel. Existing delivery behaviors include coalesced feedback and late worker completion: path generation and current state must reject irrelevant facts, and the stopped loop makes late shutdown facts inert.

## Retry policy

The run loop owns a current-path search ceiling: the smaller of the original negotiated effective ceiling and the active Transport's sealed packet ceiling. Capture the destination ceiling synchronously before resetting discovery during migration; preserve the negotiated `PathMTUInfoV1` observation. This bound governs the post-fallback searches JR1 enables, including standard discovery on that destination; pre-fallback migration behavior is outside this slice.

A retry cycle is a bounded invocation of the loss-tolerant MTU search from the current confirmed size toward that path ceiling. Initial discovery keeps the existing `maxMTUDiff` rule. Search completion (`mtuFinder.done()`) compares the confirmed size to the loss-narrowed upper bound. Jumbo restoration is a separate comparison: `confirmed > 1452 && currentPathCeiling - confirmed <= maxMTUDiff + 1`. It need not deliver the exact ceiling. Thus a completed search at 1470 of a current-path ceiling of 8972 retains its confirmed size, enables shrink detection and schedules another cooldown; it is not restored. If tolerance would terminate a retry at or below 1452 on a jumbo-permitting path, admit an explicit padded candidate at `min(path ceiling, max(1453, current size + 1))`, using the existing three-attempt loss tolerance. Each definitive loss of a live candidate consumes an attempt even when the candidate equals the ceiling and no loss bound changes. After three definitive losses the cycle ends once and schedules one cooldown; an unresolved idle probe still follows ordinary recovery rules. Only its live ACK permits growth. Failure ends that cycle at the confirmed smaller size and schedules the next interval; each new cycle reopens the candidate despite ordinary tolerance. For example, a 1468-byte ceiling settling at 1449 under a cutoff retains a future retry, which can probe 1453 after cutoff removal. A retry timer only permits a search; an ACK for its live probe is the authority to raise packet size. Keep ordinary data at the current confirmed size while a larger probe is outstanding. Discovery-probe refusal or loss is not evidence for the data-fallback detector.

| Event or state | Required transition |
| --- | --- |
| First fallback confirmed | Arm retry for confirmation time plus 60 seconds. No retry while confirmation is active or exhausted without confirmation. |
| Eligible deadline reached | Consume the deadline once and start the search if handshake confirmation, DF, discovery configuration and current-path ceiling permit it. Otherwise retain pending eligibility without a timer wake. Preserve normal send eligibility and pacing. |
| Probe ACK in the current search | Raise to the acknowledged size through the existing ACK-driven finder, admission and congestion-size update path. |
| Search completes without confirmed jumbo restoration | Keep the confirmed result; arm another search from completion time using the next backoff interval. |
| Search confirms a size above 1452 within the current-path ceiling tolerance | Stop periodic searching. Keep accumulated backoff for any later fallback. |
| Another actual fallback | Cancel any armed retry deadline and elapsed eligibility at fallback start, invalidate any running search and preserve the next interval without consuming it. Run existing reduction and confirmation again; same-path confirmation schedules exactly one next interval. |
| Retry in flight when path changes | Invalidate its callbacks and clear path-specific recovery/watch state before processing new-path feedback. Reset packetization to the effective initial size as today. |
| New path after any fallback | Run standard-size discovery immediately under existing rules. Permit jumbo only after retained cooldown expires and standard discovery admits stage two; old-path confirmation does not authorize new-path growth. |
| Shutdown | End retry with the run loop; late ACK, loss or local-refusal facts cannot restart it. |
| Discovery disabled, DF unavailable or current-path ceiling at most 1452 | No retry timer wake or jumbo search. Preserve connection-wide eligibility/backoff for a later permitting path. |

Backoff intervals are 60, 120, 240, 480, then 900 seconds, saturating at 900. Advance once per newly scheduled cycle, not per probe or ACK. An actual fallback clears a running search, armed deadline and elapsed eligibility at its start, preserving the next interval, and schedules on the same path only after its smaller size is confirmed; that confirmation consumes the next interval once. Successful growth and path migration do not reset backoff. These values are owner-approved policy, not measured network constants.

Migration retains an armed absolute deadline and the next backoff interval; it does not shorten or restart a cooldown. Elapsed pending eligibility is connection-owned and also survives migration without consuming an interval; only the newest path's standard search can admit stage two. If neither a deadline nor pending eligibility survives, a migration after any prior fallback schedules the next interval once from migration time. This includes cancellation of an active search, full restoration, unconfirmed recovery and exhausted initial-size recovery. Scheduling a new cycle consumes one interval even when migration alone caused it; repeated migration carrying a deadline or pending eligibility consumes none. An ineligible path suspends timer wakes while retaining the absolute cooldown or elapsed eligibility, so migration back to a permitting path resumes that state. Initial discovery before the first fallback keeps today's policy.

| Migration state after prior fallback | Deadline and next-interval expectation |
| --- | --- |
| First cooldown armed; migrate at 59 seconds | Preserve the original 60-second deadline and 120-second next interval. |
| That deadline elapsed while standard discovery is pending; migrate again | Preserve elapsed eligibility and 120-second next interval; no overdue wake, no old-path stage-two authority. |
| Partial result 1470 of 8972, 120-second cooldown armed with 240 seconds next; second fallback then migration before confirmation at time M | Fallback cancels the old deadline without advancing. Migration schedules M + 240 seconds, leaving 480 seconds next. Without migration, same-path confirmation schedules once from confirmation time instead. |
| Active retry, restored jumbo, unconfirmed or exhausted recovery; no retained deadline/eligibility | Schedule the next interval once from migration time, then advance its index. Same-path unconfirmed/exhausted recovery remains unable to retry. |
| Move through DF-incapable or default-ceiling Transport, then back to a permitting Transport | Suspend retry wakes; retain cooldown/elapsed eligibility and next interval. Recheck new-path standard discovery and ceiling before jumbo. At destination ceiling 1452, no probe exceeds 1452; the public negotiated ceiling remains unchanged. |

A deadline that expires before standard discovery finishes becomes one pending eligibility state, not a repeatedly overdue timer. Stage two still requires the existing successful stage-one admission condition. If the stage-one result is below that condition, retain the smaller size and schedule the next bounded search at the next interval. A same-path retry must be able to re-run the standard search from a smaller confirmed result before attempting stage two, rather than permanently trapping a path whose standard search previously narrowed.

The finder publishes one synchronous terminal result per live search identity after updating its bounds. The connection owns completion policy: it may update retry metadata, arm a cooldown from the completion fact's time and request the existing coalesced send wake. It must not restart the finder, modify recovery history or emit packets inside the ACK/loss callback. Search start remains in safe run-loop preparation. Completion publication must not depend on which receive/loss entrypoint ran or whether the loop can emit or wait. Standalone and non-primary finders retain their existing behavior without a connection completion callback.

For server migration, a newly armed retry interval starts at actual run-loop cutover, distinct from the triggering packet's receive/event time used by existing recovery bookkeeping. A retained absolute deadline or pending eligibility is carried unchanged. Client migration uses its existing cutover time for both meanings.

Use the existing connection timer. An expired deadline transitions once even if socket/congestion backpressure delays sending. Discovery remains subject to normal congestion and pacing rules, unlike fallback recovery probes. Retry adds no separate keepalive mechanism or idle-timeout override. Probe PINGs and their ACKs use ordinary idle accounting: sends and receives can refresh existing idle timers, and repeated cycles with acknowledged smaller probes can extend an otherwise idle connection. This ordinary refresh is explicitly accepted; no application-activity tracker is added. A lost discovery probe without later traffic may remain unresolved under existing recovery rules; this design promises no idle recovery deadline. Do not create a separate discovery loss clock to strengthen that contract.

## JR1 — Restore jumbo with repeatable fallback

**Status:** implementation in [JR1 (#1476)](https://github.com/GridCastIO/quicquic-go/issues/1476). Deliver as one implementation PR; it must not close design issue #1231 again. This slice is self-contained and does not require a new architecture program.

**Changes:**

1. In `packet_size_fallback.go`, separate one-time first-drop notification from recovery-episode state. Reset confirmation, loss count, packet-number boundary and recovery-probe state for each episode. Close `PathMTUFallbackV1` only on the first drop. Replace permanent-disable checks in local refusal handling, `packet_size_watch.go` and `discoveryPacketCeiling` with explicit current recovery/search policy. Preserve lower-size confirmation and exhaustion.
2. Keep retry policy and saturating deadline/backoff state in the connection-owned recovery module. Integrate eligibility advancement with `packetSizeRecoveryTime` / emission preparation and the existing timer in `connection.go`; the synchronous completion fact owns end-of-search scheduling before any wait or capacity skip. Reset watches on episode transitions and cancel old retry deadline/elapsed eligibility at fallback start. Re-enable both shrink detectors as soon as ACK-confirmed packetization exceeds 1452. A discovery probe must retain its exemption from those detectors.
3. Add a finder restart operation in `mtu_discoverer.go` that invalidates prior callbacks, starts from the current confirmed size, reopens appropriate bounds, and preserves the tested stage-one fallback and atomic report when staying on the same path. For a cooldown-driven standard re-search with a still-valid fallback, retain the report until a newly validated result replaces it. Initial-size recovery confirmation and migration retain the existing reset-to-zero contract until standard discovery republishes a result. Add the retry-specific jumbo candidate and completion rule above, without changing initial discovery tolerance. Replace the 8-bit search generation with an identity safe for repeated long-lived searches (for example, a fresh per-search identity shared by callbacks).
4. Preserve the existing run-loop ACK path for publishing size increases and updating congestion packet size; preserve emission ownership, recovery registration and buffer lifetime. Use both Reno and BBR paths. Path reset cancels search evidence before old callbacks can act and retains only connection-wide cooldown/backoff policy and elapsed eligibility. Bound post-fallback destination discovery by its sealed Transport ceiling before resetting the finder. Pass recovery event time and retry cutover time explicitly during path reset; only a newly armed retry uses the latter.
5. Update `PathMTUFallbackV1`, `PathMTUSettledV1` and `PathMTUInfoV1` comments for retries. Both channels keep their identity and one-time closure semantics. The effective ceiling remains negotiated; cooldown-driven retry does not erase a still-valid fallback report; initial-size confirmation still zeros it. Update maintained ADR language only where implementation makes it stale. This deliberately changes documented `PathMTUFallbackV1` and `PathMTUSettledV1` behavior published in v0.63.0: under [ADR 0016](0016-version-aware-compatibility.md), JR1 requires a minor release, not a v0.63.x patch. Hand this classification to the [release runbook](../runbooks/release.md), whose preparation owns the CHANGELOG.md entry and migration guidance before publication. Guidance must explain one-time first-drop signaling, later ACK-confirmed growth of transport DATAGRAM admission, possible repeated fallback, ordinary idle refresh, and the fixed consumer-published limit. This design PR publishes no release.

**Acceptance criteria:**

- After confirmed fallback and cutoff removal, the same connection on a jumbo-permitting path resumes jumbo application packets only after ACK-confirmed probe growth.
- A persistent cutoff leaves smaller application traffic usable while subsequent completed searches use the approved increasing intervals.
- A second shrink after recovery enters the existing fallback/confirmation sequence again without double-closing a public channel.
- Stale search or path feedback cannot authorize growth; unconfirmed recovery and shutdown do not start retry.
- Default and peer-capped behavior, fallback sizes, negotiated observations, first-path settled signaling and the consumer's fixed published DATAGRAM limit are preserved.
- Retry uses the existing run loop, timer, emission and send eligibility with no overdue-deadline busy wake. Ordinary probe/ACK idle refresh is accepted.
- Post-fallback migration searches respect the destination Transport ceiling while the negotiated observation stays unchanged; near-threshold tolerance cannot suppress future jumbo confirmation attempts.

**Representation and guarantee:** accepted Transport ceiling values and peer parameters are owned by existing transport validation and wire parsers; current-path/search ACK and loss facts are owned by recovery and finder identity. No new protocol parser is introduced. Behavioral evidence is example-level; no universal network-delivery guarantee is claimed. The invariants about growth authority and stale feedback are implementation requirements discharged by the finite semantic classes below.

**Artifacts and material risk:** retry is shipped behavior; probe/search authority, repeatable fallback and lifecycle invalidation are required safety enforcement. Tests are ordinary verification aids, with no new maintained diagnostic service or harness. Plan, review receipts and task pointers are process metadata. Closure triggers for stale-feedback isolation and repeatable fallback: independently reachable local refusal, remote shrink, retry, migration and shutdown can otherwise leave a live connection at an unusable packet size. One central owner is the run loop, with finder-owned probe identity.

**Blast radius and alternatives:** changes connection-local retry timing, search identity and repeated recovery transitions; adds a current-path ceiling observation and connection-owned elapsed eligibility; retry probe traffic can refresh idle timers and introduces the possibility of repeated interruptions after genuine regrowth. The published permanent-disable behavior changes and is minor-release work under ADR 0016; release preparation owns its changelog and migration notice. No global state, public configuration, schema, security boundary or dependency change. The owner's design is the adopted synchronous run-loop transition using existing clocks and callbacks. A private finder terminal fact removes the obligation to observe completion at every run-loop wait/continue site; its connection callback is synchronous and cannot reenter finder, recovery or emission. Adding another polling call was rejected because it preserves that dispersed observation obligation; revisit none. Unqualified reuse of migration reset discards same-path fallback observations and repeats unrelated migration work; rejected on merit, revisit none. Splitting retry from repeatable fallback can ship growth without recovery on the next shrink; rejected on merit, revisit none. Effects of physical-link fluctuation and probe-induced application interference remain unqualified, with no performance claim in this slice.
