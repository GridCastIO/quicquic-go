## Approach and design choices

1. **Merge order.** Squash-merge PR #1461 at `096472b3` (squash commit `S1`), then rebase PR #1462 with `git rebase --onto S1 096472b3` (head `R`), retarget its base to `main`, revalidate `R`, and squash-merge it (`S2`). Blast radius: between `S1` and `S2`, `main`'s maintained prose (conventions, ADR 0002, `AGENTS.md`) names the old path. The window lasts one hosted run of `R`; nothing is tagged or consumed from `main` in it. No other merge is admitted in the window.
   - Rejected: squash PR #1462 into PR #1461's branch, or retarget PR #1462 to `main` and merge only it. Either collapses two separately reviewed contracts into one commit and abandons PR #1461 unmerged. `none: rejected on merit` (and the assignment fixes the order).
   - Rejected: merge PR #1462's stacked head without waiting for checks on `R`. The repository requires green checks on the exact live head. `none: rejected on merit`.
2. **Final-home revalidation without changing heads.** PR #1461's head is already certified and reviewed; an empty commit or a rerun of the rewrite procedure would create a new candidate and void that. Instead rerun its five latest `pull_request` workflow runs on `096472b3` at the new home (`gh run rerun <id>`), recorded as destination check 2 of the handoff rather than a failure retry. Marking ready starts `independent-peer` on the same head. `R` gets fresh runs from its push.
   - Rejected: close and reopen PR #1461 to fire `reopened`. Same evidence, noisier history. Revisit if a rerun at the new home is refused.
3. **Re-review only what changed.** If `S1`'s tree equals `096472b3`'s and `R`'s tree equals `643f76e9`'s, no content changed and no RAS round is run for PR #1461 or PR #1462; the existing reviews stand. Destination-dependent evidence (hosted runs, links, private reporting) is certification, not a review subject. If either tree differs (only if `main` moved), the changed part is reviewed as described in stage 1.
4. **Release commit as its own PR C.** The retraction and release-record finalization go in a small reviewed PR after both identity PRs merge. Its squash commit `X` is the release commit. This keeps PR #1461 and PR #1462's reviewed heads intact.
   - Rejected: add the retraction to PR #1462. It changes a certified head, needs re-review, and the retraction belongs to the published version, not the transition. `none: rejected on merit`.
5. **Multipath evidence for `X`.** The peer job does not run on `push`. PR C is merged only when its head's parent is the live `main` tip, so `X^{tree}` equals PR C's head tree; PR C's post-ready `independent-peer` run is then evidence for `X`. The tree equality is recorded.
6. **Pre-tag consumer check through `GOPROXY=direct`.** The runbook requires a fresh no-replacement consumer at the candidate's pseudo-version before tagging. Running it through `proxy.golang.org` and `sum.golang.org` would publicly record a pseudo-version of the module before Josh approves publication and could leave a cached `@latest` answer. This check uses `GOPROXY=direct` and `GONOSUMDB=github.com/GridCastIO/quicquic-go`; every post-tag check uses the default proxy and checksum database. No query names `v0.63.0` at the proxy before the tag exists, to avoid a cached not-found answer.
7. **ADR 0014 stays unchanged.** Its statement that pre-module tags resolve and rank below v0.63.0 remains true under the retraction; the retraction is release mechanics owned by the runbook and release record. Revisit if review shows a reader would be misled.
8. **Evidence location.** Phase 1 evidence and the proposed notes go in one #1111 comment. Phase 2 results go in the release record through PR D, as Josh's decision requires for the retraction checks.
