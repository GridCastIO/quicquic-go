# Windows multipath implementation and qualification plan

**Date:** 2026-11-19. **Identity:** MP-WIN-1397, revision 3. **Status:** owner-approved planning scope; implementation and qualification pending. **Issue:** [Plan multipath support for Windows (#1397)](https://github.com/GridCastIO/quicquic-go/issues/1397). The owner approved one documentation PR through review and merge, targeting Windows amd64 with Reno primary/backup, experimental BBRv3 primary/backup and experimental BBRv3 aggregate, including the initial native-USO deferral. Completing this plan does not enable Windows multipath, authorize its implementation slices, provision infrastructure, run a qualification campaign or allocate campaign capacity.

## Outcome and source authority

Provide an actionable route from the existing Windows UDP implementation to a qualified public multipath profile. Separate production work, test infrastructure, native observations and public admission. Preserve the completed [multipath program (#646)](https://github.com/GridCastIO/quicquic-go/issues/646) and [BBR continuation (#1374)](https://github.com/GridCastIO/quicquic-go/issues/1374), their frozen evidence and their exact-result exceptions. Public support stays Linux amd64 until separately approved Windows implementation and qualification finish.

The issue's historical baseline is `48dc6634fef404404647b7e64024303a52a4fb4e`; current source was inspected at `0fbad183f7c92eba8fa234cb9194d87029e4014d`. This is a targeted comparison, not a claim that the entire repository is unchanged. Future fixtures use `github.com/GridCastIO/quicquic-go`.

The [Go Windows poller](https://go.dev/src/internal/poll/fd_windows.go) owns overlapped I/O, completion and cancellation; inspect the selected toolchain sources when qualifying, rather than treating the moving source page as a versioned receipt. Keep that runtime route. The completed Windows datapath decision rejects direct custom overlapped/blocking I/O that duplicates the runtime's machinery or changes deadline/close semantics.

The platform seam must classify facts before connection policy acts. The Windows implementation needs separate cases for timeout/local capacity (`WSAEWOULDBLOCK`, `WSAENOBUFS` and runtime deadline errors), known message-size rejection (`WSAEMSGSIZE`), socket-wide failure, destination-specific failure and failed deadline operations. Preserve error identity/wrapping; do not import Linux `sendmsg`/`EPERM` retry or `EIO` GSO fallback rules into Winsock. Confirm actual reachable wrapping at the selected Go boundary. Ambiguous submission stays uncertain rather than being described as definitely unsent. A generic `WSAEINVAL` is not proof of offload failure: Windows also uses it to reject outgoing CE. W2 must also port `nativeEndpoint.writePublic`, whose public error mapping is separate from `localEndpointBackpressure`: preserve the native error and the applicable `errors.Is` matches for `ErrMultipathBackpressureV1`, `ErrMultipathDeadlineV1` and `ErrMultipathUncertainV1`. An attempted capacity failure can report both backpressure and uncertainty; queued expiry is definitely unsubmitted. Reuse the expectations in `TestEndpointPublicErrorCertainty` with Windows-reachable inputs.

The [ECN receipt](../audits/2026-09-23-windows-ecn-w2/README.md#native-representation-and-results) observed successful zero-byte payload results with complete peer delivery, with and without ECN OOB. Current managed native sends normalize that case, while the Unix endpoint treats an unexpected count as a short write. W1 must make Windows success normalization explicit at the exact native send seam used by the granted route, including protected members, scalar segments and public/stateless writes. Preserve nonzero short results, errors even when the count equals the payload length, and raw observations in native evidence. Arbitrary wrapper callbacks gain no normalization authority. W2 must state and test the resulting public `WriteTo` count/error behavior against the preserved successful-datagram contract; do not hide uncertainty behind a successful count.

Extract Windows metadata support under the transport's existing initialization/read ownership. The [Winsock ECN contract](https://learn.microsoft.com/en-us/windows/win32/winsock/winsock-ecn) supplies native int32 metadata and separate IPv4/IPv6 receive options. Reuse the recorded mapped-IPv4 outgoing ECN encoding at IP level, while preserving `packetInfo.pktinfoV6` for IPv6-level packet-info replies on dual-stack sockets. Inspect the actually admitted families; a failed unused family must not disable a single-family socket, and a failed required family disables ECN for the dual-stack socket. Qualify malformed/truncated metadata recovery, outgoing permitted marks, native CE rejection and opt-out. ECN capability does not bypass per-path ECN validation or change the controller's CE response contract.

The initial scalar profile requires effective `UDP_SEND_MSG_SIZE` and `UDP_RECV_MAX_COALESCED_SIZE` values of zero on caller-owned sockets before granted I/O. A caller can preset either option; skipping URO activation or omitting a send CMSG does not establish its current value. The existing USO capability probe discards that value. Under the [Winsock UDP socket-option contract](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-udp-socket-options), nonzero presets change datagram framing and are outside this initial scalar profile. W2 must choose and document enforcement before first granted I/O: an explicit caller precondition or read-only inspection with refusal that preserves the caller's settings. Cover each preset independently in the existing grant/offload cases; do not silently clear caller configuration or infer permission to use URO.

W2 must provide a checked scalar receive path for eligible caller-owned granted sockets, where URO is off: validate read flags and decoder validity, discard malformed/truncated metadata and continue to later valid traffic. The current ordinary `readOrdinaryPacket` path does not supply that guarantee, and merely reusing its call is insufficient. Publish the admitted-family setup result as `connCapabilities.ECN` before the client/server recovery constructors consume it; the native ordinary wrapper must preserve that capability. The granted reader also adopts the existing managed Windows receive-publication rule: on both scalar and URO reads, publish `ECNUnsupported` when endpoint ECN qualification is false, even if a successfully enabled family still supplies a valid mark after opt-out or partial setup failure. Preserve payload and packet info. The existing metadata fallback case must inject marked ingress for that family, observe useful delivery and unchanged ACK/PATH_ACK ECN counters, preserve usable unmarked outgoing traffic, and separately observe valid marks when qualified plus recovery after malformed input. This changes only the new granted route; Unix receive-publication policy, ordinary ungranted Windows and managed-lease behavior retain their existing contracts.

The selected policy is endpoint-wide qualified ECN: a non-negotiated ordinary peer sharing a granted endpoint consumes that grant's ECN capability too. Do not add a negotiation-specific ECN switch. The managed-ECN ADR's ungranted ordinary boundary remains unchanged; W5 records the effective grant/ECN state as well as scalar/USO state so any cost difference is interpreted against the capability actually exercised.

W2 must trace socket capability through path opening and same-ID migration. At this baseline, `sentPacketHandler.admitPath` inherits root ECN eligibility, while `pathCreditRegistry.commitTuple` restarts ECN validation without passing a replacement capability. The native writer receives a mark already selected and registered by recovery, so dropping its CMSG alone would make accounting inconsistent. At the existing deterministic Reno path-transition seam, open or migrate from an ECN-capable origin to an ECN-disabled target and require useful unmarked target traffic plus agreement between outgoing metadata and recovery's recorded mark. The connection/recovery owner must use the target socket's capability at the transition; any required runtime repair belongs to W2's separately approved implementation contract, with existing-platform preservation. Ordinary peers after absent negotiation also retain `AddPath`/`Probe`/`Path.Switch`. Their separate owner, `Conn.switchToNewPath`, resets recovery through `sentPacketHandler.MigratedPath` without passing the target capability; fixing only the negotiated owners does not cover this route. Apply the same qualified-origin/disabled-target expectation to the existing granted ordinary switch fixture: useful post-switch delivery, unmarked target traffic and matching recovery accounting. These are mixed-capability instances of the existing migration/ECN obligation, not an additional platform or campaign inventory.

Scalar-first egress means no Windows `UDP_SEND_MSG_SIZE` is emitted by the endpoint writer. Do not merely advertise GSO support to a native encoder whose non-Linux helper is a stub. Trace `nativeOrdinaryConn.capabilities`, emission grouping and path-route fallback so either the granted route advertises scalar production or any preserved grouping is split deliberately by the writer without a native-GSO claim. Every software segment checks permission and the original deadline; accepted prefix, uncertain current member and untouched suffix remain distinct. Ordinary ungranted USO stays with `windowsConn`. Future native USO requires its own Windows CMSG construction, successful-count interpretation, safe fallback classification and lifetime evidence; neither it nor a performance target is smuggled into W1/W2.

URO remains a read-owner concern. Preserve its bounded decoder, copy-out lifetime, metadata inheritance, one-time malformed-coalescing fallback and post-read-loop buffer release. Initial opt-out or failed URO activation selects scalar receive. If disabling already-active URO fails, keep the guard armed: discard suspicious oversized reads lacking a segment record and continue splitting reads with valid records, as `TestWindowsUROGuardTurnOffFails` requires. Hardware engagement is a separate observation: the [earlier URO receipt](../audits/2026-09-11-w3-uro-results.md) needed a second endpoint across a virtual NIC; its single-host run did not engage URO. Microsoft's [URO rules](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/udp-rsc-offload) require compatible headers, including ECN, for coalescing. Option success, a large read buffer or loopback traffic alone is not engagement evidence.

## Independent peer, ordinary cost and aggregation

Reuse the maintained [independent-peer fixture](../../interop/multipath/README.md), pinned picoquic `fbd46d9a1f54ebf9397f2ee6355b5019ab379fb7` and PicoTLS `e446233b4100ebcdec60901c05bfb7f4cd369c5d`. The current Go tests/runner, C socket adapter and Docker venue are Linux-oriented. Recommend a native Windows subject talking over an explicit test network to the pinned peer on Linux: this keeps the independent protocol implementation unchanged and avoids making a Windows port of its POSIX UDP adapter a prerequisite. W4 must adapt subject/peer address and port configuration, process supervision, timeouts, result collection and cleanup; the current same-host/loopback assumptions cannot simply be reused across hosts. Remote orchestration is a verification-aid obligation with joined processes and retained failures, not a new runtime control channel. A native Windows peer port remains an alternative if separate-peer coordination proves more costly; changing peer pins or wire behavior requires an explicit disposition.

Preserve the eight Reno scenarios in both roles: useful transfer, absent negotiation, path-zero ACK, key update with a silent path, status/backup failover, abandon/reopen/late feedback, same-ID migration/rebinding, and unequal MTU/invalid frame. Carry the separate negotiated-zero vectors/controlled-peer evidence without claiming the pinned independent peer supplies that oracle. BBR primary/backup and aggregate each retain useful transfer, abandon/reopen/late feedback and same-ID migration/rebinding in both roles. These identify the existing semantic inventory, not a newly allocated Windows campaign. The existing peer's IPv4 examples do not replace the native metadata family's IPv6/dual-stack cases.

For aggregate useful transfer, snapshot per-path counters after both paths become active, offer identifiable new STREAM and DATAGRAM content during that phase, and require independent useful receipt on both actual ingress paths. Pre-activation cumulative DATAGRAM counts and sender scheduling deltas alone are insufficient. Preserve exact payload checks, missing/duplicate/skip rejection and subprocess join. A failed first Windows run must be attributed between fixture readiness and product behavior before any retry decision.

W5 adapts the maintained [ordinary cost workload](../../ordinary_cost_test.go) and [driver](../../interop/multipath/ordinary_cost.py) for both Reno and BBR, including missing BBR bulk coverage. Compare unregistered ordinary traffic, ordinary traffic on a granted endpoint, and negotiated configurations with phase-appropriate controls. Cover bulk STREAM, short DATAGRAM, mixed traffic and stateless/control pressure. Record each comparison arm's effective grant, ECN and scalar/USO state; ordinary peers on a qualified granted endpoint inherit ECN, while ungranted ordinary Windows behavior stays unchanged. For lifecycle memory, observe negotiated idle, a validated backup, active aggregate and retirement against a suitable negotiated comparison state; an unregistered ordinary connection cannot be the backup-path control. Distinguish application content, packet tracking, controller bookkeeping and pending local-send storage. No production telemetry expansion is implicit.
