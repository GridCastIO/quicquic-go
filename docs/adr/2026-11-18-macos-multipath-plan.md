# macOS multipath implementation and qualification plan

**Date:** 2026-11-18. **Identity:** MP-MAC-1396, revision 4. **Status:** owner-approved planning scope and controller/policy profile; implementation and qualification pending. **Issue:** [Plan multipath support for macOS (#1396)](https://github.com/GridCastIO/quicquic-go/issues/1396). The owner approved including BBR and aggregation while retaining the two-path cap, and authorized this documentation PR through review and merge. This document proposes future work; neither its acceptance nor completion of issue #1396 enables macOS multipath, starts a qualification campaign, allocates campaign capacity, or authorizes the implementation slices below.

## Recommended initial target

Target native `darwin/arm64` with the existing Linux controller/policy combinations: Reno primary/backup, experimental BBRv3 primary/backup, and experimental BBRv3 aggregate. Reno remains the default, and Reno aggregate stays unsupported. Qualify the combinations in stages without introducing a Darwin-only controller restriction. Defer `darwin/amd64` and other Darwin kernel majors until their own native evidence exists; narrowing the approved controller/policy outcome requires an explicit evidence-based owner decision.

Retain the current public cap of two active or validating protocol paths, including path zero. This is an existing repository-wide limit, not a Darwin restriction. Raising it changes the shared path-credit, resource, scheduling and lifecycle contract and is separate work; macOS enablement does not expand the common path count.

## Darwin replacements for Linux qualification methods

Use the existing private `configureNativeIO`/`startNativeEndpoint` seams in root-package tests for pre-admission endpoint work. Add a Darwin-tagged fixture rather than relaxing the Linux fixture's tags around Linux-only mechanics. Keep fake errno injection in explicitly simulated tests. Do not add an exported qualification bypass, a production environment override, a fake OS identity or a second deadline owner.

For EAGAIN-to-deadline feasibility, adapt the archived Darwin construction to the selected scalar UDP path: set a modest socket send buffer on a fresh owned test socket, read back capacity B, verify an ordinary-size ECT(0) positive control, then use valid payload plus ancillary data whose combined socket-space demand exceeds B. Exercise the production `WriteMsgUDPAddrPort` call with the request's absolute deadline. Capture syscall results where the venue permits, a goroutine stack through the actual Go `internal/poll` write/wait path, the deadline return, result classification and peer observations. The [Go poller source](https://go.dev/src/internal/poll/fd_unix.go) identifies the EAGAIN/waitWrite seam; the receipt must bind the exact installed toolchain source rather than infer behavior from the moving web source.

This construction is induced send-buffer insufficiency, not evidence of sustained network/device congestion. A raw C errno observation alone is not Go poller traversal; a test wrapper returning EAGAIN outside Go's poller is simulated; an already-expired deadline tests pre-dispatch handling rather than a blocked native call. If the target cannot demonstrate actual traversal and bounded return, record the missing evidence and stop qualification for a maintainer decision. Do not replace it with a Linux container result or declare success after a skipped case.

Use that same current-write witness for independent queued expiry and active-close/join. For retry/deadline continuity, retain deterministic first-send EPERM assertions and exercise production-reachable Darwin scalar writes. Constructed segmented members can test the shared writer's prefix/deadline rules, but their grouping is not evidence of production Darwin packet construction. Darwin reports GSO disabled, so native Linux GSO-EIO fallback is not a required Darwin kernel case. A simulated retry input may precede native scalar traversal only if the receipt labels the boundary explicitly. Test real scalar EMSGSIZE separately as size feedback, not timeout/backpressure.

Keep a separate bounded socket-pressure observation: fresh UDP sockets, observed send-buffer values, controlled sender/receiver load and native writer-stack sampling. Record whether any actual pressure wait occurred, immediate local errors and their classifications, loss/drop counters where available, and native return timing. If UDP ENOBUFS is not observed, retain that explicit residual; the archived AF_UNIX observation is not a UDP witness. An unread loopback receiver or a small buffer does not by itself prove sender pressure. A missing pressure wait is an explicit negative observation, not a failure to rescue with unbounded retries; sufficient deadline qualification still needs its separate native traversal witness. Real interface/device pressure requiring privileged network configuration is a maintainer decision outside this planning issue.

Measure deadline/tolerance behavior without a syscall tracer; tracing supplies attribution only. Preserve the existing 20 ms bound and responsive-scheduler assumption. Record performance-core versus efficiency-core activity and actual test scheduling/topology where observable. The available host has 12 performance cores and four efficiency cores; an aggregate load average is insufficient reason to call a run contaminated, and background efficiency-core activity is not equivalent to performance-core contention. No process termination, new affinity policy or exclusive machine reservation is implied.

## Ordinary cost, BBR and aggregation evidence

Before admission, compare unregistered ordinary QUIC with the same native source/binary using the endpoint grant. Cover STREAM, DATAGRAM, mixed bulk and stateless/public response pressure, plus idle/backup/retired-path memory and active-close completion. On Darwin, ordinary sends may use the separately qualified `sendmsg_x` route while the granted endpoint receives scalar packets from the production sender; preserve that real comparison and retain the private-syscall opt-out as a distinct fallback check. Do not manufacture a Linux GSO-on cell on a platform with no GSO.

Report application goodput, CPU per useful byte, native RSS, relevant application-call latency, offered/received stateless traffic, losses/local disposals, close and join outcomes. Reuse metric definitions and applicable numerical criteria from [R18](2026-10-24-multipath-reno-plan.md#r18--measure-ordinary-peer-costs-on-granted-endpoints), including the 1.10 CPU ratio and 10% RSS growth limits; preserve raw results. The later qualification protocol must identify valid Darwin measurements and comparable workloads before execution. It must not import Linux's exact accepted CPU exceptions or silently create new tolerances. Approval of this plan does not choose a new sample count, statistical campaign or budget.

BBRv3 primary/backup is part of the initial Darwin target. It requires its own ordinary-cost disposition, per-path sampling/recovery and native buffer-lifetime evidence, plus the existing six BBR peer cases: useful-transfer, abandon/reopen/late-feedback and same-ID migration/rebinding in each role. Exercise both configuration setter orders, clones and server-selected configurations. Carry shared endpoint evidence only where source and exercised behavior justify it; Reno-only native observations cannot stand in for BBR's protected-member or feedback behavior. The separate full-controller qualification program remains outside this work and is not a new prerequisite.

BBRv3 aggregate is also part of the initial target. Preserve the same three peer scenarios in both roles under explicit aggregate selection. The existing useful-transfer case demonstrates per-path DATAGRAM delivery before simultaneous activation and new both-active STREAM traffic afterward. M2 must extend the latter phase: snapshot per-path DATAGRAM counters after activation, offer identifiable payloads while both paths stay active, and require the independent peer to associate at least one identifiable fresh payload with each actual ingress path during that phase, in both client/server roles. Keep sender deltas as scheduling evidence; delivery on only one path cannot satisfy the useful-receipt requirement. M3 runs the resulting witness natively; an unchanged port of the current cumulative assertions is insufficient. A first-run failure remains inconclusive until fixture failure is distinguished from Darwin behavior. The existing hosted peer invocation covers Reno defaults, so an aggregate Linux control is an option for separately approved attribution work, not evidence already supplied by CI.

Add scoped native comparisons on balanced disjoint, unequal delay/rate and shared-bottleneck conditions. Use matched ordinary BBR single-path and independent-pair controls, an explicit primary/backup comparison and the existing shared-bottleneck Reno competitor where its fairness metric is used. Report application goodput, CPU/useful-byte, memory and useful-delivery/latency separately from functional correctness. Existing B11 metric definitions and topology reasoning are reusable design material; its retired executable is not a maintained dependency, and its Linux observations are not Darwin evidence. The later approved protocol must choose the finite measurement inventory and applicable criteria before collection, without allocating them in this planning issue.

MP-MAC-ME owns measurement readiness before M3. Adapt the maintained ordinary-cost workloads for both Reno and BBR, including the currently missing BBR bulk cells. Preserve per-process CPU accounting through native `getrusage`, and collect per-process peak resident memory through Darwin `getrusage(RUSAGE_SELF).ru_maxrss`, whose native unit is bytes; normalize explicitly when comparing with the Linux fixture's reported kB, and retain raw units. Peak RSS does not measure memory retained at a particular path state: ME must also supply a live or retained-memory observation on a negotiated connection at idle, with a validated backup and after retirement, with a phase-appropriate comparison state identified in the protocol. An unregistered ordinary connection cannot be the backup-path control. Replace `/proc`/`taskset` assumptions with native process and performance/efficiency-core activity observations selected in the executable protocol; missing attribution is inconclusive, not presumed quiet. This does not authorize CPU pinning or exclusive host use.

ME must give each reported loss/disposal metric an observation point. The current ordinary fixture reads `ConnectionStats().PacketsLost`, whose production increment belongs to the Reno/CUBIC owner; mark that counter unavailable for BBR rather than treating zero as no loss. Report relay-observed drops where a relay exists, receiver delivery gaps at the receiver, and local disposals at the endpoint. Leave network drops unmeasured when the workload has no observing source; this plan does not authorize new production telemetry.

For topology readiness, use a separately scoped native userspace UDP relay successor based on the archived B11 queue design: distinct rate-limited queues for disjoint paths, different rates/delays for unequal paths, and one shared bottleneck queue for the shared case and Reno competitor. Validate queue identity, configured rate/delay/drop behavior and realized delivery before measurement; do not silently substitute PF/dummynet or privileged host-network changes. Record the relay's CPU cost and timing limitations. The topology and host-accounting method, fixture ownership and finite readiness checks must be concrete in the later protocol before it can authorize collection. This assigns missing infrastructure, not a campaign budget or a new product dependency in this PR.

Keep experimental, uncoupled and no-general-fairness limitations. No Linux aggregation gain, controller qualification or accepted cost exception is a Darwin claim. Missing or unacceptable evidence leaves the affected public activation unmerged; a reduced Darwin controller/policy profile requires the owner's explicit decision on the concrete evidence. Do not silently ship Reno-only or primary/backup-only as completion of the approved target.

## Ownership, artifact classes and alternatives

The current PR is process/traceability metadata only. Contract closure is **not triggered** for a documentation-only change: it introduces no runtime invariant or enforcement mechanism. Its representation domain is the finite source inventory, explicit proposed platform/configuration table and named semantic classes; source facts are checked against Git at the recorded revision. Its guarantee is example-level planning/evidence applicability, not universal platform correctness. Added links are verified against Git paths, not through a new Markdown parser or general link-checking product.

Future runtime platform/admission code is shipped behavior and required support enforcement. Existing endpoint and connection owners retain deadline, buffer, recovery, protocol and lifecycle authority. New fixtures, native drivers and CI are verification aids; receipts and support records are metadata. Before any future aid becomes a maintained blocker, its slice must explicitly approve its payoff (detect native ownership/wire regressions), domain (the selected profile and semantic cases), owner (transport test suite/interop maintainer) and retirement policy (equivalent replacement or feature removal). This planning PR does not itself impose new CI gates or recursive fixture-completeness obligations.
